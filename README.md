# ocvpn

Прозрачная маршрутизация **только** эндпоинтов [opencode](https://opencode.ai) через VLESS-VPN, чтобы обойти IP-based rate-лимиты free-тарифа. Весь остальной трафик хоста не затрагивается.

> Почему это нужно: free-тариф opencode лимитирует по IP (без device_id). Смена IP сбрасывает лимиты. Скрипт каждый запуск выбирает случайный рабочий сервер из твоей подписки — новый выходной IP.

## Как работает

1. Скачивает подписку с VLESS-ключами (умеет plain-text и **base64** — V2Board/Marzban)
2. Берёт 10 случайных поддерживаемых серверов, параллельно пингует их (TCP-connect)
3. 5 лучших по пингу — кандидаты; пробует реальное подключение через xray (HTTP 204 на `google.com/generate_204`)
4. Первый рабочий ключ → прозрачный прокси (iptables REDIRECT)
5. **Только** трафик к IP-адресам `*.opencode.ai`, `zenmux.ai`, `ai.zenifra.com`, `auth.openai.com` на порту 443 идёт через VPN
6. Всё остальное на хосте — напрямую (nginx, SSH, приватные сети, остальной интернет)

Каждый запуск = новая случайная выборка → новый ключ → новый выходной IP.

## Подписка

Поддерживаются plain-text и **base64** подписки. Приоритет URL:
`OCVPN_SUBS_URL` (env) > `~/.ocvpn-subs-url` (файл) > встроенный fallback-список.

```bash
# Положить свою (платную) подписку в файл — токен не попадёт в git
printf '%s\n' 'https://provider.example/sub/TOKEN' > ~/.ocvpn-subs-url
chmod 600 ~/.ocvpn-subs-url
```

Учитываются только ключи `vless://` типов `tcp`(raw)/`ws`/`grpc`/`xhttp`, которые умеет генерить xray-конфиг скрипта. Типы, которые xray не потянет (например sing-box xhttp packet-up с `extra=`), отфильтровываются.

## Быстрый старт

```bash
# Клонировать и запустить
git clone git@github.com:OTumanov/ocvpn.git
cd ocvpn
bash ocvpn.sh
```

Скрипт автоматически:
- Установит xray (если не найден) в `~/.local/opt/xray`
- Скачает список ключей
- Найдёт рабочий сервер
- Поднимет прозрачный прокси

После успешного запуска — запускай opencode как обычно.

## Команды

| Команда | Описание |
|---------|----------|
| `bash ocvpn.sh` | Запустить VPN, найти рабочий ключ, настроить маршрутизацию |
| `bash ocvpn.sh --cleanup` | Снять iptables-правила, убрать форсировку IPv4 из /etc/hosts |

## После запуска

Скрипт выводит статус и остаётся висеть в foreground. Чтобы запустить opencode — открой новую сессию/вкладку и запусти `opencode` как обычно. Маршрутизация работает на уровне ядра (iptables nat), поэтому opencode автоматически ходит через VPN без переменных окружения.

Для смены ключа (и IP) — `Ctrl+C` и запусти `bash ocvpn.sh` заново (новая случайная выборка).

## Проверка, что VPN работает

```bash
# Внутри скрипта уже проверяется рабочий ключ. Внешне можно убедиться так:
curl -s https://ipinfo.io/ip          # IP хоста (без VPN)
curl -s --proxy socks5h://127.0.0.1:10808 https://ipinfo.io/ip   # IP через прокси — должен отличаться
```

## Тесты

```bash
bash ocvpn-tests.sh    # ожидается PASS=5 FAIL=0
```

Покрывает:
- Парсинг всех типов VLESS-конфигов (reality, ws, tls, grpc, xhttp)
- Декодирование URL-encoded параметров (path, sni)
- Xray 26: `xhttpSettings` (host строкой, mode), а не устаревший `httpSettings`
- Логику отбора кандидатов (TCP-пинг, сортировка, отбрасывание мёртвых)
- Фильтр поддерживаемых ключей (`is_supported_key`)
- Индемпотентность /etc/hosts (не плодит дубликаты при повторных запусках)
- Парсинг 5 реальных ключей из живой подписки

## Ограничения и заметки

- Правило `owner --pid-owner` (исключение трафика самого xray) работает не на всех ядрах (iptables-nft). Если не поддержан — пропускается: петли не будет, т.к. REDIRECT ловит только opencode-IP:443, а xray ходит на IP VPN-сервера.
- Время жизни публичных/дешёвых ключей ограничено: если скрипт не находит рабочий — просто запусти ещё раз, выборка случайная.
- Если упал и не снял правила: `bash ocvpn.sh --cleanup` вернёт iptables и `/etc/hosts` в исходное состояние.

## Зависимости

- `curl`, `python3`, `unzip`, `iptables`
- Рут (для iptables и установки xray)
- Linux (проверено на Ubuntu и в Docker с `NET_ADMIN`)

## Что не трогает

- Nginx / проксируемые сайты (80, 443 входящие)
- SSH (22)
- Приватные подсети (10.0.0.0/8, 192.168.0.0/16, 172.16.0.0/12)
- Docker-сети
- Существующие TCP-соединения (iptables nat OUTPUT работает только на новые)

## Порты

| Порт | Назначение |
|------|------------|
| `10808` | SOCKS5 прокси (localhost) |
| `10809` | HTTP прокси (localhost) |
| `12345` | Прозрачный прокси (iptables REDIRECT) |

SOCKS5 и HTTP прокси слушают только на `127.0.0.1` — наружу не публикуются. Прозрачный порт `12345` (dokodemo-door) слушает на всех интерфейсах, но трафик на него попадает только через iptables REDIRECT (никакие процессы снаружи достучаться не смогут, т.к. порт не публикуется наружу).

## Конфигурация

Параметры в начале скрипта:

```bash
BATCH_SIZE=10    # сколько случайных ключей пинговать
MAX_TRIES=5      # сколько лучших кандидатов пробовать
PING_TIMEOUT=3   # таймаут TCP-пинга (сек)
TIMEOUT=5        # таймаут теста generate_204 (сек)
```
